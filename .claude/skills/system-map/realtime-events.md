# Realtime events (websockets) — system map

Purpose: every websocket endpoint and event type across backend, web and mobile, so you don't have to re-read `consumers.py` / `ChatRoom.jsx` / `ConversationsScreen.tsx`.

Verified at commit c1d44c5 (2026-10-26); updated in PR `fix/reliability` (server-broadcast messages, close codes, reconnect backoff, mobile heartbeat), and pending `perf/list-refetch` (web `conversation_update` handling).
Refresh: `git diff --stat c1d44c5..HEAD -- backend/chatapp/consumers.py backend/chatapp/views.py frontend/src mobile/src`, then update only the affected rows and bump the commit line.

## Wiring
- `backend/core/asgi.py`: `ProtocolTypeRouter` → `http` = Django; `websocket` = `URLRouter(chatapp.routing.websocket_urlpatterns)`. There is **no** auth/session middleware; consumers authenticate the JWT themselves.
- `backend/chatapp/routing.py` (live): `ws/presence/` → `PresenceConsumer`; `ws/socket-server/<room_name>/` → `ChatConsumer`.
- `backend/chatapp/urls.py` also has a `websocket_urlpatterns` list (`<int:conversation_id>` kwarg). It is **dead**: asgi doesn't use it, and the kwarg name doesn't match the `room_name` the consumer reads.
- Channel layer: Redis when `USE_REDIS_REALTIME` is set, otherwise in-memory (`CHANNEL_LAYERS` in `core/settings.py`). Production runs `daphne` (`Procfile`).

## Auth (`PresenceTrackingMixin.get_user_id_from_token`, shared by both consumers)
Checks run in this order; the first token found wins:
1. `Authorization: Bearer <jwt>` header (mobile).
2. `lv_access` cookie (`AUTH_COOKIE_ACCESS`, web). Accepted only if `_origin_is_allowed()` passes: no Origin header is OK (native clients); otherwise the Origin must be in `CORS_ALLOWED_ORIGINS`, match the handshake `Host`, or match explicit `ALLOWED_HOSTS` (the `*` entry is ignored).
3. Legacy `?token=` query param. Web sends it only on localhost when a legacy token is in storage (`getLegacyAccessToken`). Slated for removal.

The token is validated with SimpleJWT `AccessToken` (1 h lifetime). Neither consumer re-checks expiry once the socket is open.

### Presence semantics (`consumers.py`)
- `Profile.ws_connection_count` counts every open socket (presence and chat) across processes. It changes only through atomic `F()` UPDATEs.
- `increment_presence`: if the user is already online and `last_seen` is fresh → count+1 and return "not new". Otherwise → count+1, `is_online=True`, `last_seen=now`, and return "came online". A stale online row is treated as coming online, so contacts get told again.
- `decrement_presence`: count>1 → count−1. count≤1 and online → `0`, `is_online=False`, `last_seen=now`, and return "went offline". The loop retries 3× on races.
- Freshness: a user counts as online only when `is_online` is true **and** `last_seen` is within `ONLINE_FRESHNESS_SECONDS` (90). The same rule is used by `get_online_contact_ids` (initial list) and `ProfileSerializer.get_is_online` (REST).
- Heartbeat: web (`Layout.jsx`) and mobile (`RootNavigator` and `ConversationsScreen` presence sockets, via `services/realtime.ts` `startPresenceHeartbeat`) send `{"type":"heartbeat"}` every 20 s. `PresenceConsumer.receive` writes `last_seen` at most once per `PRESENCE_TOUCH_INTERVAL_SECONDS` (60) per socket, measured from connect or the last touch (monotonic clock). `touch_presence` also skips the write if another socket touched `last_seen` within the last 30 s. The chat socket ignores heartbeats.
- Audience: `get_presence_contact_ids` returns users who share a conversation with this user, minus blocked pairs in either direction. Presence and typing are only ever sent to the `presence_user_<contact>` groups, never globally. Contacts are cached per socket for the online event and re-read for the offline event.
- `POST /api/presence/offline/` (`mark_presence_offline_view`, called by web logout) forces count=0 and offline, then sends `broadcast_presence_update(False)`.
- `reset_presence` management command runs in `Procfile` `release` (migrate → reset_presence → collectstatic). It sets count=0 and `is_online=False` for everyone, clearing counts left behind by crashed dynos.

Count: 20 distinct wire types in use (`heartbeat`, `initial_online_users`, `presence_update`, `typing_status`, `conversation_update`, `message_created`, `message_deleted`, `user_typing`, `user_stopped_typing`, `message_status`, `message_reaction`, `message_edited`, `message_pinned`, `webrtc_offer`, `webrtc_answer`, `webrtc_ice_candidate`, `call_accept`, `call_reject`, `call_end`, `call_invite`; mobile also accepts the alias `messageReaction`). Five of them run in both directions.

**Broadcast message payloads** (`message_created`, `message_edited`, `message_reaction`, `message_pinned`) go through `serializers.message_broadcast_payload`, which drops the per-user fields `PER_USER_MESSAGE_FIELDS` = `current_user_reaction`, `can_translate`, `translated_text`, `translated_source_language`. Clients keep their own values when merging (spread) and derive `current_user_reaction` from `reactions[].user_id`; a new message defaults `translated_*` to null and `can_translate` to "not mine and has text". REST responses still carry the full per-user serialization.

## Client socket lifecycle
- **Reconnect policy (web)**: `utils/reconnect.ts` `getReconnectDelayMs` = exponential backoff with jitter (0.5–1 s, 1–2 s, 2–4 s … capped at 15–30 s), reset on a successful open. While the tab is hidden no reconnect is scheduled; `visibilitychange` reconnects when it is shown again. On an auth close (`SOCKET_AUTH_CLOSE_CODES` {1008,4401,4403}) the socket stops and calls `refreshSessionOnce()` once per successful connection; a successful refresh (from here or from any REST 401, see flows §1) dispatches `session-refreshed` (`SESSION_REFRESHED_EVENT`), and a socket stopped for auth reconnects once on that event.
- **Web presence** (`layout/Layout.jsx`): one socket per logged-in tab, keyed on `user.user_id`. Heartbeat every 20 s. Reconnect policy above. Closed on logout (`handleLogout` also calls presence/offline and logout). Listeners subscribe via `usePresence().subscribeToPresenceEvents` (`context/PresenceContext.jsx`).
- **Web chat** (`pages/Conversations/features/ChatRoom.jsx`): one socket per open conversation. Reconnect policy above. The per-effect `isDisposed` flag ignores stale sockets. `socketStatus` drives the UI. Messages sent while the socket was down are not replayed on reconnect (they appear on the next history fetch).
- **Mobile presence**: **two** sockets while the Chats tab is mounted; both heartbeat every 20 s (`services/realtime.ts`). `navigation/RootNavigator.tsx` handles only `conversation_update`; it reconnects with the same backoff + jitter (`getReconnectDelayMs`), doesn't reconnect while the app is backgrounded (an `AppState` "active" listener reconnects), and on 4401/4403 calls `refreshAccessToken()` (`services/api/client.ts`, single-flight) once per successful connection and reconnects only if that returns a token. `screens/ConversationsScreen.tsx` handles presence/typing/conversation_update and never reconnects. Both send `Authorization: Bearer` from `tokenStorage` (`services/storage.ts`). WS base = `API_BASE_URL.replace(/^http/,"ws")`.
- **Mobile chat** (`ConversationsScreen`): opened for `selectedConversation.id`. It also re-runs when `isFocused` changes, so switching tabs drops and reopens it. No reconnect.

## Known gaps / bugs
1. ~~Mobile never sends `heartbeat`~~ — fixed in `fix/reliability` (both mobile presence sockets heartbeat every 20 s).
2. **Chat sockets count toward presence but cannot heartbeat.** A user with only a chat socket open goes stale after ~90 s.
3. ~~The chat relay trusts client fields~~ / 4. ~~`deleteMessage` relay has no authorization~~ / 5. ~~New messages reach an open chat only through the client relay~~ — fixed in `fix/reliability`: the REST views broadcast `message_created`/`message_deleted` from the DB and the consumer ignores client `chat`/`deleteMessage` frames. Remaining: a socket that was down misses broadcasts (no replay on reconnect); web `ChatRoom` doesn't refetch on `conversation_update`.
6. ~~Expired access token on web~~ — fixed in `fix/reliability`: global refresh-and-retry on 401 (patched `fetch` + axios) and sockets refresh once on 4401/4403 (see flows §1).
7. **Expired token on mobile.** Sockets reuse the stored access token, refreshed by an HTTP 401 or (RootNavigator only) by a 4401/4403 close. `ConversationsScreen` sockets just die and don't reconnect.
8. Mobile has no WebRTC calls. Web never sends or handles `call_invite`.
9. ~~`message_reaction` payloads are serialized for the actor~~ — fixed: broadcasts omit per-user fields (see "Broadcast message payloads").
10. Web `conversation_update` is handled only while `ConversationList` is mounted (`/conversations*`). On other pages `Layout.jsx` refetches the list itself (2 s debounce) so the nav badge and browser `Notification` stay live; while the tab is hidden it defers to the next focus / entering `/conversations*`, presence reconnect, or the > 60 s hidden rule.
11. Web logout calls `presence/offline`, which zeroes the count while other tabs' sockets are still open. That user then shows offline until another socket connects.
12. The ChatConsumer close code is 4403 even for a missing or expired token (presence uses 4401). Clients treat both codes the same (refresh once, then stop).
13. Presence and typing events are filtered by block, but the chat room itself is not: a blocked pair can still relay typing and call events over an already-open chat socket. REST POST is blocked.
14. Dead `websocket_urlpatterns` in `chatapp/urls.py`.
15. A web chat socket rejected for a non-auth reason (non-participant, deleted conversation) also triggers one session refresh and one reconnect attempt before stopping.
